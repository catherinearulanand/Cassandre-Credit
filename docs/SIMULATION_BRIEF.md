# Simulation brief: what you are showing, what is real, what is not

Written for the person presenting the platform. Read the one-page summary first; the rest is the
detail behind each line.

## One-page summary

**What the demonstration is.** Four synthetic borrowers are replayed through the platform from
sanction to closure (or to default and recovery). Production code runs every decision. The things
outside the platform (the core banking system, the people who approve, the data feeds) are stand-ins,
and every step on screen says which.

**Really connected (live, just now):**
- **PaddleOCR**, the open-source engine, running locally in its own isolated environment and reading
  synthetic statement pages. It is the first real, third-party recogniser in the build.
- **All platform logic**: rules engine and 20 rule packs, covenant engine, CTS, limits, drawing power,
  drawdown gate, SMA/ECL, RFA, early-warning, calendar, stressed assets, recovery, closure, review,
  maker-checker, signed approvals, hash-chained audit, the four agents and their guards, the model
  gateway's policy engine, the Finacle **adapter**.
- **Machine learning**: LightGBM early-warning and breach models, trained and evaluated on the
  synthetic book.

**Simulated (a stand-in with the same interface):**
- **Finacle**: an in-process simulator. The adapter in front of it is real; the system behind it is not.
- **People**: officers, checkers, committees, recovery head. Scripted, labelled "(simulated human)".
- **Borrowers and their data**: names, financials, sanction letters, scanned statements, conduct and
  defaults all come from a generator with exact ground truth.
- **External feeds** (GST, Account Aggregator, bureaus, MCA/CERSAI, ratings, news): not connected.
  Seven of fourteen early-warning indicators have synthetic feeds; the other seven are reported as
  "not evaluable" and flagged as a data gap rather than read as clear.
- **Storage and messaging**: in-memory stores and an in-process event log stand in for Postgres and Kafka.
- **Keys**: software keys stand in for an HSM.

**Not built at all:** an LLM (so drafting uses deterministic templates), the hosted PaddleOCR call
(adapter written, waiting for your key), SSO/MFA/mTLS/SIEM, Temporal/Neo4j/Feast, the web UI and API.

**The honest headline numbers (all synthetic):**
- PaddleOCR on 6 synthetic pages (135 figures): 118 correct, 101 passed straight through, **0 wrong
  among those**. RapidOCR on the same pages: 131 correct, 80 straight through, 0 wrong.
- In the demo, PaddleOCR passed 44 of 45 figures straight through correctly on two borrowers and 45 of
  45 on another, with 0 wrong; the remaining figure went to a reviewer.
- The full OCR release gate is **failing** on the earlier larger run (a second statement layout is read
  poorly). We say so rather than hide it.

## How to run it

```
python -m tools.integration_status --deep      # probes each connection, runs a real PaddleOCR read
python -m sim.demo_story --engine paddle       # the four journeys, ~3 minutes on this CPU
python -m sim.demo_story --engine none         # same story without OCR, 3 seconds
python -m sim.run_simulation                   # 600-borrower accuracy simulation (covenants, gate, SMA, models)
python -m ocr.eval.compare_engines             # PaddleOCR vs RapidOCR on the same pages
```

## The four journeys

Each journey is a real run; the steps are in `reports/demo_story.json` and on the artifact page.

| Journey | What it shows | Real | Simulated |
|---|---|---|---|
| **Steady borrower** | Sanction letter read and compiled to a CTS with citations; CTS published with maker-checker; limits pushed to Finacle; statements read by PaddleOCR; covenants tested; an edited receivables figure caught by accounting identities; a drawdown approved by the ten-check gate and disbursed; repayment and closure with a zero-dues proof and document release in time | Compiler, CTS service, adapter, PaddleOCR, covenant engine, gate, closure | Finacle, the approvers, the pages |
| **Covenant breach** | Net Debt/EBITDA breached; the Covenant Agent proposes consequences and drafts a reservation-of-rights letter; the agent's own human is **refused** as approver; a second officer approves; the gate then refuses a new drawdown | Engine, agent runtime, maker-checker, gate | Officers, Finacle |
| **Stress to default** | Conduct worsens; early-warning climbs; the account goes SMA-2; a red-flag file opens and the fraud-classification proposal is **refused before natural justice**; after show-cause and the response window the committee closes it; 60 days of non-payment ages the account to NPA with an IRAC provision; the stressed-asset clock starts; the Recovery Agent analyses a settlement and a recovery head approves at delegated power; overdue documents climb the chase ladder | EWS, SMA, RFA, stressed assets, recovery, calendar | Borrower behaviour, committee, recovery head |
| **Negotiated agreement** | The grammar cannot read it (7 unresolved fields); the platform stops and routes it to a human, where an LLM would read it. **This is the one place the demo shows a gap rather than a capability.** | Compiler fallback | The human; the LLM does not exist |

## What is simulated, in detail

1. **The borrowers.** `libs/testing/synthetic` builds fictitious companies with checksum-valid PAN, GSTIN,
   CIN and LEI, financial histories for 13 quarters and sanction letters, in a standard and a negotiated
   style. Ground truth is exact, which is what lets us measure accuracy at all.
2. **The documents.** Statements are rendered as images (two layouts, six fonts) and degraded
   (skew, blur, noise, compression) in four tiers. PaddleOCR reads these images; nothing in the
   generator is shared with the reader except the page itself. Stamps, handwriting, photographed pages
   and multi-page tables are not simulated.
3. **The conduct and the defaults.** A latent stress process drives utilisation, overdrawn days,
   returned cheques and delays. Three realism features keep the models honest: measurement noise,
   defaults from shocks nothing can foresee, and recoveries without default. The generator and the
   models share assumptions, so model scores here are an upper bound on real performance.
4. **Finacle.** `simulators/finacle_sim` imitates idempotency keys, a change feed and injected faults.
   The adapter, the signed approvals and the gate-decision check are real. Replacing the simulator with
   the bank's Finacle API is a configuration and certification exercise, not a redesign.
5. **The people.** Scripted principals with the right roles and scopes. The controls are real: the
   system refuses the wrong person, which the breach journey demonstrates. Only the judgement is scripted.
6. **The external world.** No feed is connected. Where the platform would use GST, bureau or news data it
   either has a synthetic series or reports the indicator as not evaluable.
7. **Time.** The story is replayed on a controlled clock from June 2023 to October 2026. Rule packs are
   evaluated as of the run date (21 Oct 2026).
8. **Drafts.** The letters and notes come from deterministic templates because no LLM is attached. The
   guards that would police a model (number binding, concession screen, required wording) are real and
   tested, but have not been exercised against a real model.

## What "really connected" means for PaddleOCR

- **Local worker (connected).** PaddleOCR 3.7 / PaddlePaddle 3.3 run in `.venv-paddle`, an isolated
  Python environment, behind a pipe. Images never leave the machine, so this mode meets the India
  residency and zero-retention terms and is the one to use with real borrower documents.
  Every call passes through the same validator as any vendor (word boxes required, geometry and
  confidence checked, nothing guessed) and is logged by image hash without content.
- **Hosted API (awaiting key).** The adapter is written; set `PADDLEOCR_API_URL` and
  `PADDLEOCR_API_TOKEN` (see `.env.example`). Two cautions. The request and response shapes follow the
  PaddleX serving convention and are **unverified against a live endpoint**; if the shape differs, the
  validator rejects the page and sends it to manual spreading, so nothing is mis-read silently.
  And the service is operated outside India, so the code allows it for **synthetic data only**; real
  borrower documents must stay on the local worker or an India-hosted instance.
- **Speed.** On this CPU a page takes about a minute, against about six seconds for RapidOCR, because
  Paddle's CPU acceleration (oneDNN) fails on these models in this build. A GPU, or the hosted API, removes the problem; it
  does not affect correctness.
- **Accuracy.** On six synthetic pages PaddleOCR matches RapidOCR on safety (zero wrong figures passed
  straight through) and passes more figures through, but reads fewer correctly (118 of 135 against 131).
  Six pages is a smoke test with wide intervals, not a benchmark. The full harness
  (`python -m ocr.eval.harness --engine paddle`) is the proper comparison and needs faster hardware.

## What would change with real connections

| Replace | With | What it takes |
|---|---|---|
| Finacle simulator | The bank's Finacle APIs and CDC | Agreed API/event versions, certification, idempotency guarantees from Finacle |
| Scripted people | SSO with roles and scopes from the bank directory | OIDC/MFA integration; directory lookup for agents' principals |
| Software keys | HSM/KMS provider | A key provider implementation behind the existing interface |
| In-memory stores | Postgres, object storage, Kafka | Adapters behind existing ports (ADR 0002) |
| Templates | A self-hosted model for negotiated agreements; a frontier model for letters | A model, a golden set, and the evaluation the guards were built for |
| Synthetic feeds | GST, Account Aggregator, bureaus, MCA/CERSAI | Consents, contracts, one adapter each |
| Rule pack contents | Verified RBI text | A named person checks each pack and flips it to `verified` |
| Synthetic pages | Consented real scans | The same harness, run on real data, is the only evidence a customer should accept |

## Limits to state out loud when presenting

- Every accuracy figure is on synthetic data with exact ground truth. None is a claim about real scans,
  real sanction letters or real defaults.
- The OCR release gate is failing on the larger earlier corpus; coverage on a second layout is the weakness.
- The breach forecast shows no skill beyond a simple headroom rule; the early-warning model is only
  modestly better than counting fired rules.
- No LLM is connected, so nothing about LLM drafting quality is measured.
- Nothing is independently validated (see `docs/VALIDATION_PACK.md`).
- Rule packs are unverified against RBI text.
